# Branch and Tag Strategy

This document describes the branch layout and tag naming convention for MonoTune.

---

## Active Branches

| Branch | Purpose |
|--------|---------|
| `dev` | Main development branch. All feature work targets `dev`. Default integration branch. |
| `release/0.10.x` | Maintenance branch for the 0.10.x release line. Bug-fix cherry-picks only. |
| `feature/*` | Short-lived feature branches. Merged into `dev` via pull request when ready. |

All other branches from the OuterTune upstream (`canary`, `fdroid`, `lite`, `weblate-staging`,
`feature/library-manager`, `release/0.6.x`–`release/0.9.x`) have been deleted.
Run `.github/workflows/cleanup-repo.yml` (once, manually) to apply this deletion on the remote.

---

## Tag Naming Convention

```
v{major}.{minor}.{patch}
v{major}.{minor}.{patch}-a{N}    (alpha)
v{major}.{minor}.{patch}-b{N}    (beta)
v{major}.{minor}.{patch}-rc{N}   (release candidate)
```

**Examples:** `v0.10.2-b1`, `v0.10.2-rc1`, `v0.10.2`

### Tag Normalization

The following tags use non-standard naming inherited from OuterTune and will be renamed
by `cleanup-repo.yml`:

| Old tag | New tag |
|---------|---------|
| `pre_rel-0.10.0-rc1` | `v0.10.0-rc1` |
| `pre_rel-0.10.1-b1` | `v0.10.1-b1` |
| `pre_rel-0.10.2-b1` | `v0.10.2-b1` |
| `v0.8.0-final` | `v0.8.0` |
| `v0.9.0-final` | `v0.9.0` |

All historical `v0.6.x`–`v0.9.x` tags and `v0.10.0`, `v0.10.1` are kept unchanged.

## Remaining Gaps

### Monochrome Integration

`MonochromeClient` in `monochrome/MonochromeClient.kt` is a stub — all methods return
`MonochromeResult.Error("Monochrome backend not yet implemented")`.  Once the backend
endpoint spec is finalised the following work is needed:

1. Replace `MonochromeClient` with a real HTTP (or gRPC) implementation.
2. Wire `MonochromeClient.search()` into the search UI so Monochrome results appear
   alongside YTM results.
3. Implement the track-matching pipeline that populates `monochrome_track_match` rows
   (query `MonochromeClient.search()` using YTM title + artist, pick the best match,
   write `MonochromeTrackMatch` via `MonoTuneDao.upsertMonochromeMatch()`).
4. In `MusicService`, prefer `MonochromeClient.resolveStreamUrl()` over the YTM stream
   when a confident match (or manual correction) exists for the current track.

### YTM Scrobble Functionality

The `ytm_scrobble_queue` table and `MonoTuneDao` scrobble methods are in place.
What is still missing:

1. **Enqueue on playback** — at the point where a track is considered "played" (e.g.
   after 30 s or 50 % of duration), call
   `database.enqueueScrobble(YtmScrobbleQueue(songId = …, playedAt = …, durationPlayedMs = …))`.
2. **Drain worker** — create a `WorkManager` `CoroutineWorker` that:
   - Calls `database.getPendingScrobbles().first()` to fetch un-scrobbled entries.
   - Calls `YouTube.registerPlayback(…)` for each entry (see `innertube/YouTube.kt`).
   - On success calls `database.markScrobbled(entry.id)`.
   - Schedules itself with exponential back-off on failure.
3. **Schedule the worker** — schedule the drain worker from `MusicService` after each
   track completes.

### YTM Search / Playlist Sync

YTM search, liked songs, and playlist sync are fully retained from OuterTune.
`SyncUtils.kt` handles playlist/liked-song synchronisation via `YouTube.*` calls.
The remaining gaps relative to full parity with the Monochrome roadmap are:

1. **Monochrome search results** — once the client is live, surface Monochrome tracks
   in `SearchScreen` alongside YTM results.
2. **Playlist sync for Monochrome matches** — when a synced YTM playlist is loaded,
   pre-compute Monochrome matches for its songs in the background so stream URLs are
   ready without per-track latency.

## Next Steps

The items below are the remaining tasks, in suggested order.
Each can be tackled as a standalone PR targeting `dev`.

### 1 — Clarify `PlaylistEntity.isLocal`

The `isLocal` field on `PlaylistEntity` marks user-created playlists that are not
synced to YTM.  It is **not** related to the local media scanner and should be
retained.  Update the `TODO(MonoTune)` comment in `PlaylistEntity.kt` to reflect
this so future contributors are not confused.

### 2 — Export Room schema 22.json

Run a successful Gradle build (any variant) so KSP generates
`app/schemas/com.dd3boh.outertune.db.InternalDatabase/22.json` and commit it.

### 3 — Implement the YTM scrobble drain worker

- Create `app/src/main/java/…/workers/ScrobbleWorker.kt` extending
  `androidx.work.CoroutineWorker`.
- Fetch `database.getPendingScrobbles().first()`, call `YouTube.registerPlayback()`
  for each entry, and call `database.markScrobbled(entry.id)` on success.
- Schedule the worker from `MusicService` with exponential back-off on failure.

### 4 — Monochrome API connection

Once the Monochrome backend endpoint spec is finalised:
- Replace the stub implementations in `MonochromeClient.kt` with real HTTP calls.
- Wire authentication, search, stream URL resolution, and track-matching into the
  player pipeline.
- Implement the Monochrome track-matching background job that populates
  `monochrome_track_match` rows via `database.upsertMonochromeMatch()`.
